# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Read first

`AGENTS.md` is the authoritative brief (scope, authorized work, file-ownership rules between agents). Before any UI/UX/iconography/imagery decision, apply the project skill `.agents/skills/otear-product-design/SKILL.md`. Then read only the relevant sections of `docs/UX_GUIDELINES.md`, `docs/MOTION_GUIDELINES.md`, `docs/FRONTEND_CONVENTIONS.md`; `PRODUCT.md` (authorized capabilities) and `DESIGN.md` (visual language) bound what screens may exist. When planning modules, also read `docs/context/alcance-multisector-y-feedback.md` and the matching file in `docs/planning/`.

Hard scope limits:

- Frontend-only validation demo with **synthetic** data. Do not build the Go backend, real ingestion/analysis/storage/sending, auth, or payments. Never present a simulation as real (the UI already says so, e.g. "Pago registrado solo en esta demo").
- Multisector (agricultura, carreteras, construcción, vigilancia, minería a cielo abierto). The agro lote → vuelo → comparación → observación → informe flow is one scenario, not the core model.
- `docs/context/matriz-dorfman-provisional.md` is provisional; the GPS-less photo policy and "G6" are unresolved — don't resolve them silently.
- Recurrence, urgent requests, packages and advisory are proposals to validate, not features to build. The landing (`features/landing/`) is multisector and sector-agnostic: agricultura, carreteras, construcción, minería and vigilancia are only examples (`cases` in `landing-page.tsx`), followed by a «Su sector» card and an «A su medida» section (`customSteps`) saying any sector fits and new components can be made per sector. Keep that honest: vocabulary/campos propios are built; per-sector components (complementos) are a proposal, worded «Se construye con usted». Never ingenio-only.

## Commands

Node 22, npm, committed `package-lock.json`.

```bash
npm ci
npm run dev             # Turbopack; use dev:webpack / build:webpack if Turbopack hits a port restriction (sandbox)
npm run check           # next typegen + tsc --noEmit, eslint --max-warnings=0, prettier --check
npm test                # unit tests of the pure logic
npm run audit:ui        # Lighthouse + axe + overflow/12px/weight audit of 8 routes (needs out/ or --build); see docs/planning/ui-audit/README.md
npm run build
npm run format          # prettier --write (src, root *.ts/json/mjs)
```

`npm test` runs `src/**/*.test.ts` with the Node test runner (`scripts/run-tests.mjs` compiles them first because this Node has no TypeScript support). Test files import siblings with a `.ts` extension and must not use the `@/` alias or React; keep tested logic in pure modules (`geo.ts`, `insights.ts`, `integrity.ts`, `billing/*.ts`). Add behavior tests only for material behavior; no placeholder suites or markup snapshots.

## Architecture

Next.js 16.4.3 (App Router), React 19, TypeScript strict, Tailwind 4, HeroUI 3 (global CSS, no provider), Leaflet, Lucide. `@/*` → `src/*`. Next.js here differs from older versions: check `node_modules/next/dist/docs/` before non-trivial framework work. `next dev` rewrites the "NOT the Next.js you know" block in `AGENTS.md`; commit it with your diff rather than reverting.

**Routing.** `/` just redirects to `/programacion`. All screens live under the `src/app/(workspace)/` route group (`programacion`, `vuelos`, `mapa`, `evolucion`, `equipos`, `informes`, `pagos`, `documentos`); its `layout.tsx` wraps them in `DemoProvider` + `AppShell`. Page files are thin and only render one feature view (e.g. `vuelos/page.tsx` → `FlightReviewView`).

**Shared demo state — the key cross-file concept.** `src/features/demo/demo-context.tsx` is a single client-side store (`useDemo()`) holding sites, flights, findings, invoices, payments, documents, selected site/flight, and a `notice` toast message. Every module reads and mutates through it, so a flight scheduled in `programacion` appears in `vuelos`, `pagos` and `documentos`. Things to know:

- Collections are filtered by the selected `siteId` before being exposed; `payments` is not.
- Changing site resets `selectedFlightId` to `flight-${siteId}-01` — seed data must keep that id convention.
- State is in-memory only; `resetDemo()` restores `demo-data.ts`. Nothing persists across reloads.
- Types (`Site`, `Zone`, `Flight`, `Finding`, `Invoice`, `Payment`, `FlightDocument`) are in `features/demo/types.ts`; sector-specific naming comes from data (`Site.zoneLabel`, `sectorLabel`), not from forked models. Add new shared entities there rather than in a module.
- Mutations that must not rewrite identity (`id`, `siteId`, `flightId`) are guarded inside the update functions — preserve that when adding new ones.

**Features vs shared UI.** Domain UI lives in `src/features/<domain>/` (`flights/planning`, `flights/review`, `billing`, `compliance`), each view next to its CSS module. `src/components/` holds only genuinely shared pieces (`app-shell`, `drone-preview`, `maps/`, `ui/`). `src/lib/format.ts` holds shared formatters. Promote code to `components/` only when several consumers exist.

**Modules added after the first four.**

- `mapa` (`features/sites/mapping/`): wizard that proposes a site outline (flight history, KML/GeoJSON, deed area, LiDAR `.las` header, hand drawing) and splits it into zones (equal parts, by flights via k-means + Voronoi, by production CSV, by levels, by chainage). Roads are a polyline split by PK; other sectors are polygons. `replaceZones` in `demo-context` re-links flights and findings by geometry. The geometry lives in `src/lib/geo.ts`.
- `informes` (`features/reports/`): history and insights computed only from session data (`insights.ts`), plus a consolidated text report.
- Traceability (`features/traceability/`): document templates with auto-fill, SHA-256 fingerprints, signatures that become invalid when content changes, and per-item evidence in the pre-flight list (`requirements.ts` maps items to evidence). Items and their labels in `preparation-items.ts` are stored by flights, keep them stable.
- Servicios (`/servicios`, `features/services/`): three actors (`Party`: manager = ingenio, owner = cañicultor, operator) and the contracting flow as a pure state machine in `workflow.ts` (tested; requested → quoted → assigned → scheduled → delivered ⇄ disputed → verified → invoiced, or cancelled; `availableActions` says what each role can do). `use-services.ts` runs a step plus its side effects: scheduling creates a flight, delivering completes it, invoicing creates the invoice (price × billed ha, or flat per flight). `links.ts` `coveredHaFor` lets Pagos and the operator table read hectares from either the flight log or the delivery. «Ver como» is `actingAs` in `demo-context` (selector only; no real auth). Seeds: `initialParties`, `initialServiceRequests`. Market reasoning: `docs/context/mercado-cana-ingenios-y-sistemas-existentes.md`.
- Pagos automation (`features/billing/`): reads UBL electronic-invoice XML, reconciles a bank CSV, and a "before paying" list (`readiness.ts`). Nothing is sent anywhere.

**Revisión por roles y funciones de la segunda fase.** Cinco personas simuladas revisaron la landing y la demo (informes y reparto en `docs/planning/revision-usuarios/`, plan en `docs/planning/revision-por-usuarios.md`); son hipótesis, no resultados de usuarios. De ahí salieron cuatro funciones, todas con datos de ejemplo y sin avisar a nadie:

- **Seguimiento hasta el cierre** (`Finding.followUp`, `features/flights/follow-up.ts`, puro y probado; UI en `flights/review/follow-up-panel.tsx` y `measure-board.tsx`): responsable, plazo, estado abierta / en corrección / cerrada, cierre solo con nota, historial y «vencida» calculada contra `FOLLOW_UP_TODAY`, que es la misma constante que `DEMO_DATE` (25 oct 2026: hay un solo «hoy» en toda la demo). `taskAssigned` se conserva y es verdadero exactamente cuando hay `followUp`. Las sugerencias de IA sin revisar no tienen medida. Evolución e Informes cuentan abiertas, en corrección, cerradas y vencidas; el informe consolidado trae «Seguimiento de medidas correctivas».
- **Responder a una disputa** (`services/workflow.ts`, acción `reply`): el operador acepta el ajuste (solo si se cobra por hectárea), sostiene lo entregado con nota obligatoria y soportes, o corrige y vuelve a entregar; con las dos primeras la solicitud vuelve a `delivered` con `disputeReply` visible. La regla de tolerancia del 5 % no se tocó (decisión comercial).
- **Motivo de la elección** (`assign(..., reason)`, `ServiceRequest.assignReason`, hasta 160 caracteres): lo ve quien contrata y lo recoge `reports/decisions.ts`; el operador no lo ve. `delivery.coveredHa` es opcional: un servicio cobrado por vuelo no declara hectáreas.
- **Informe del vuelo firmable** (plantilla `flight-report` en `traceability/templates.ts`, `FlightReportSigning`): firman «Operador» y «Revisor o interventor»; la misma persona no puede firmar dos roles (regla de la demo, no una norma). Sin valor legal y el texto lo dice. El «Acta de entrega» se abre desde la misma sección. La autorización «predio» se lee según el sector (`placeWordsFor`); el rol guardado sigue siendo «Propietario o administrador».
- Pestañas por URL: `/vuelos?tab=resumen|evidencias|hallazgos|informe` y `/informes?tab=pendientes|evolucion|costos|informe`.

Decisiones del dueño vigentes (30 oct 2026): precio, datos y piloto siguen «por definir» en la landing; el operador entrega los vuelos; agricultura es el caso principal de la landing y los otros cuatro son ejemplos; las tarifas de ejemplo rondan los $30.000/ha, siempre «de ejemplo». Sigue sin decidirse: tolerancia pactada en el pedido, vista propia del operador y vista de un ingenio con varios cañicultores.

**Asistente de IA «Próximo vuelo» (`features/agents/`, in Programación).** `flight-proposal.ts` (pure, tested) scores every zone from the site's own history (sustained vigor decline and stalled progress from `evolution.ts`, confirmed findings, repeated findings via `compareWithHistory`, days since last flight, never-flown zones), skips zones already in an upcoming flight, and proposes up to four with a route from `planMission`; it also lists «oportunidades» (unreviewed findings, operator-declared shortfall, steady zones that could be spaced out, comparisons without control points). It is explicit rules, not a model: every point carries its sentence and numbers, the UI says «Sugerido por IA · ejemplo» (`components/ui/ai-badge.tsx`, reusable for the image and price agents) and nothing is scheduled until the person presses «Preparar este vuelo», which prefills `FlightForm`; the saved flight keeps `Flight.origin` (reasons + approval date). `next-flight-assistant.tsx` is the strip under the page title plus the dialog. Seed note: in agriculture the 29 October flight (and its service request) skips the second lot via `bookedZoneIds` in `demo-data.ts` so there is something to propose; the other sectors show the «ya está en la agenda» case. Weights are a starting point to validate. Research and positioning: `docs/context/agentes-de-ia-y-diferencial.md`.

**Asistente de IA «Imágenes» (`features/agents/image-candidates.ts` + `suggestion-*.tsx`, in the Hallazgos tab of Vuelos).** The assistant's candidates are ordinary `Finding`s with `Finding.suggestion` (confidence band, evidence, what a photo cannot tell, photo span as fractions of the flight's photo sequence); status `pending` means «por revisar», and nothing becomes the person's observation until they confirm it. They are hand-written examples in `demo-data.ts` (`imageCandidates`; two per site on the latest flight, the second deliberately weak, plus three already-reviewed ones in older flights so the track record «2 de 3 confirmadas» exists), not model output, and the UI says so. Pure logic (tested): `sourceLabel` (the source line follows the review), `suggestionStats` (reviewed only; «pocas» under 5), `reviewQueue`, `photoRangeText`, `caution` (low confidence, or high priority + low), `historyNote` (via `compareWithHistory`). Suggestions are excluded where they would distort other numbers: Evolución counts for security (`buildCaptures` skips pending ones), the operator table (`operatorSummaries`) and the «antes de pagar» pending-findings check (`readiness.ts`). Map markers of suggestions have a dashed border (`.is-suggested`). Dismissing does not train anything and the UI says it.

**Asistente de IA «Cotizaciones» (`features/agents/quote-reading.ts` + `quote-advisor.tsx` + `ceiling-hint.tsx`, in Servicios).** For whoever buys (manager or owner; hidden from operators), on requests in `requested`/`quoted`. `readQuotes` (pure, tested) compares each quote with the request's ceiling and window, with the **median of what the same company agreed before for the same kind and unit** (`referenceFor`; never a market tariff, there is no market data in the demo), with the other quotes, with each operator's earlier deliveries on this site (`operatorRecord`: last coverage % under 95, returned services) and with what its note does not say (`unstatedTopics`: deliverables, travel, repeating the flight, sensor, product for applications; the questions can be copied, nothing is sent). It names an operator only when that quote is no worse on any measurable axis (price, start date, coverage, returns); otherwise it lays out the trade-off. It never assigns; «Asignar» stays in the table. Quotes over the ceiling or starting after the window are left out of the comparison. `CeilingHint` in «Nueva solicitud» suggests a ceiling 25 % above the reference (`suggestedCeiling`, a starting point). Roads skip coverage by area (a line has no hectares). In the seeds the agriculture request «Vigor del cultivo» shows a real trade-off (cheaper vs earlier start and better record); other sectors have no same-kind history for it, so they compare quotes only among themselves.

**Flight routes (`features/flights/mission-plan.ts`).** Pure and tested: `planMission` builds each seeded flight's route from the zones it covers and the sector (parallel survey lines along the narrowest direction for agriculture and construction, an out-and-back along both sides of the centre line for roads, a loop inside the fence for security, plus a façade loop for construction), and derives distance, minutes, photos and hectares covered from it (camera values are representative, not a product's). `demo-data.ts` runs it for every flight; do not hand-write `distance`/`duration`/`photoCount`/`coveredHa` for seeded flights. Routes with more than 14 points show only the take-off marker on the map. Research and the plan for the flight simulation (Viper aircraft, painted coverage): `docs/context/simulacion-de-vuelo.md`.

**Flight replay («Simulación», `features/flights/replay/` + `track.ts`).** On the Resumen and Observaciones maps (`SiteMap` takes `replay`), a flight's planned route is replayed: `buildTrack` (pure, tested) rounds the corners to a turning radius, gives a speed that drops in turns, scales the time to the flight's recorded duration, and derives the moments (take-off, each finding at its closest pass, return, landing), photo times and the time each sampled cell of the zones is first reached. `playback.ts` (pure, tested) is the shared clock; `use-replay.ts` owns the track, the clock and the open state in `FlightContent`, so both tabs show the same instant; `replay-bar.tsx` is the controls and readings. On the map, `components/maps/replay-layer.ts` draws the swath reached (one stroke, so overlapping passes do not darken), the trail and the lit findings, and `replay-drone.ts` draws the aircraft on a small WebGL canvas moved to its position (the brand «Viper» by default, or the generic family of the flight's equipment; the DJI models are not used there, their licence is unresolved), with a flat SVG silhouette when WebGL is missing. It is labelled as illustrative (the area reached never feeds `billing/coverage.ts`; only the operator's declared hectares do) and a scheduled flight is a «Vista previa». The aircraft is fixed-size on screen, not to scale. Reduced motion: no play or speed, stepping by moments only. Plan and sources: `docs/context/simulacion-de-vuelo.md`.

**Layout language.** All four modules share one pattern: a textured rail of rows (`.rail-panel` in `globals.css`; flights use `features/flights/flight-timeline.tsx`, Pagos and Documentos have their own row lists) beside the map/detail, instead of stacked cards or tables. The drone sits in a dark-green "hangar" panel (`DronePreview tone="dark"`). Topographic textures are static SVGs in `public/textures/`. Motion is CSS-only (exponential ease-out, stagger via `--i`).

**Drone 3D.** `components/drone/` renders a procedural quadcopter with `three` (the one extra dependency, lazy-loaded via `next/dynamic`; no animation library). Drag/inertia/keyboard live in `drone-scene.tsx`, geometry in `drone-model.ts`. Seven generic aircraft families (`DroneKind`: compact, enterprise, hexacopter, heavy-lift, sprayer, fixed-wing, vtol) plus the four DJI GLBs form the model gallery (`features/drones/drone-gallery.tsx`, a wide dialog in the manner of a simulator's aircraft picker: grid of 3D stills grouped by purpose, sector filter, big model to turn around, «Usar»). It opens from «Ver modelos» next to the «Dron» field of the flight form (writes `DroneOption.equipmentName`, which `droneOptionFor` maps back to the same card; tested) and from «Ver otros modelos» in `features/flights/planning/drone-hangar.tsx` (illustration only, it does not change the flight's equipment). The stills come from one shared offscreen renderer (`components/drone/drone-thumbnail.ts`, queued and cached, loaded only when the gallery opens; a card per live canvas would exhaust WebGL contexts) and fall back to an icon without WebGL. Labels, categories, sectors, real equipment names each shape resembles (`examples`) and the equipment-name mapping live in `features/drones/drone-catalog.ts`; to add a model, add it there (and a builder in `drone-model.ts` for a new generic family, plus `parts-catalog.ts` and `replay/aircraft.ts` labels). Only the DJI files are real models; the real names under a generic family are «se parece a», never a claim of likeness. It falls back to a text message when WebGL is unavailable. The landing uses a fifth, brand-only procedural aircraft, «Viper» (`BrandKind` in `drone-model.ts`, built from the logo's glider: V-tail, upturned wing, rear pusher propeller; livery with the company logo on the left wing and «VIPER» on the right); it is not a fleet family, so no catalog, parts or marks refer to it. It is also the aircraft drawn in the flight replay on the maps. On the landing it is not drawn by `drone-scene.tsx` but by `features/landing/flight-scene.ts` (mounted by `drone-flight.tsx`, own chunk): a fixed, click-through, orthographic canvas seen from above. It arrives flying from the side (~3.4 s, no scroll lock), loiters in circles over the hero slot, and while the page scrolls it follows a route (`flight-path.ts`, pure and tested: Hermite through waypoints keyed by scroll) with stops measured from the DOM — `[data-drone-slot]`, `[data-flight-perch="head"]` on each section header (it rests in the empty space to the right of the title) and `[data-flight-perch="home"]` on the footer logo. Heading and bank come from its real on-screen velocity; when the scroll stops it loiters again; the shadow is the same model drawn flat through a stencil. Reduced motion: parked over the hero, scrolls away with the page. New sections that should be a stop need `data-flight-perch="head"` on their header. It also loads four official DJI CAD models converted to GLB (`public/models/dji/`, listed in `djiOptions`). Their licence is UNRESOLVED: do not publish or redistribute them; see `docs/context/investigacion-listas-informes-modelos-3d.md` (also covers how they were converted). Research behind reports, itinerary, payments and signatures: `docs/context/investigacion-reportes-itinerario-pagos.md`.

**Evolución (`/evolucion`, the product differentiator).** `features/evolution/`: `evolution.ts` (pure, tested: `buildCaptures` from completed flights' `Flight.capture`, plan vs actual via `Site.schedule`, pace/projection, stalled zones, sustained NDVI declines, comparison reliability from `Flight.log`), `narrative.ts` (plain-language reading), `line-chart.tsx` (SVG, table fallback), `evolution-view.tsx` (time rail + slider/play + compare; per-sector visual). The building is `components/evolution/building-scene.tsx` (schematic three.js, not a reconstruction); roads/agro/security colour `ParcelMap` zones through `zoneColors`. Values are seeded in `demo-data.ts` (`captureSeries`). Concept and what real data would need: `docs/context/evolucion-en-el-tiempo.md`. For construction sites the stage can show a survey file per capture date (LAS, XYZ, GLB, OBJ, PLY) read in the browser (`components/evolution/model-loader.ts`, pure parsers and the deliverables table in `features/evolution/point-cloud.ts`); everything else is refused with advice. What surveys deliver and what is supported: `docs/context/entregables-levantamiento-obra.md`.

**Fleet (`/equipos`).** `features/fleet/`: `fleet.ts` holds the maintenance logic (plans by hours/months, battery cycles, alerts, airworthiness, costs, pilot summaries); aircraft, batteries and maintenance live in `demo-context`; flights reference `aircraftId`. Part condition on a 3D model: `fleet/condition-map.tsx` (UI) + `components/drone/condition-scene.tsx` (three.js). Marks (`PartMark`, `demo-context` `partMarks`) store a point in the model's own coordinates plus the `modelKey` they were placed on; the scene paints a coloured spot per mark with a patched `MeshStandardMaterial` (`onBeforeCompile`, up to 24 marks) so it works on any mesh granularity, including user-loaded `.glb` scans (read locally via object URLs, kept per aircraft in a module-level map, never uploaded). Open "Cambiar" marks raise a danger alert in `aircraftAlerts`; seeded points were picked on the DJI GLBs, so changing those models invalidates them. Marks store a part id from `fleet/parts-catalog.ts` (manufacturer names from the manuals, free-licence names for generic aircraft; anchors in `parts-anchors.ts` are approximate and in the model's own coordinates, front toward -z, which is why the M350 spec has `yaw: Math.PI`). DJI manuals are not free-licensed: only names and diagram numbers are cited. Sources, what is official vs my translation, and the per-model maintenance intervals found: `docs/context/nomenclatura-partes-aeronaves.md`. Clicking the model selects a part (name label + painted area, `PartCard`); marking a condition is a separate action. The usage heat map (`parts-usage.ts`, `usage-panel.tsx`) is computed from logged hours, flights and battery cycles since each part's last service against the aircraft's own plan intervals (flight-driven parts assume 1.5 flights/hour); colours are relative between the parts shown on the model. `MaintenanceRecord.partId` restarts a part's count.

Area-priced services: `billing/coverage.ts` + `area-check-card.tsx` compare ordered (zone polygons), covered (`FlightLog.coveredHa`, reported by the operator) and billed (`Invoice.billedHa`) hectares inside «Antes de pagar»; mapping can import named polygons (`parseZones` in `geo.ts`); Informes has an operator table (`reports/operators.ts`). Market reasoning: `docs/context/mercado-cana-ingenios-y-sistemas-existentes.md`. Model and sources: `docs/context/modelo-de-personalizacion.md`, `docs/context/personalizacion-por-empresa.md`.

**Landing → demo conversion (`features/entry/`, `features/landing/sector-picker.tsx`, `lead-form.tsx`).** The landing's «¿Qué opera usted?» picker stores the visitor's sector in `localStorage` (`otear.entry`, parsed defensively in `entry.ts`, tested). «Abrir la demo» sets `launch`; `DemoEntry` (workspace layout) consumes it once: selects the matching example site, applies the sector preset (`applyPreset`) and shows a welcome notice. `DemoInvite` is a dismissible card offered once per session after ≥45 s and three screens or one action; it never takes focus. The contact form has no server and no third-party service: it is two steps (name, email, sector → send), and the second step builds a ready-written message (`lead-message.ts`, pure and tested) that the visitor sends from their own WhatsApp (`NEXT_PUBLIC_WHATSAPP_NUMBER`) or mail (`NEXT_PUBLIC_CONTACT_EMAIL`, `mailto:`); `NEXT_PUBLIC_BOOKING_URL` adds a calendar button. Nothing is received until the visitor sends it, so abandoned forms leave no trace. Unset channels show as «Pendiente» in dev and are hidden in production. A real receiving endpoint would be a backend and is out of the demo's scope. The drone's arrival is skipped when the page loads already scrolled, so `/#contacto` lands on the form. Visits to the landing (not the demo) are counted only if `NEXT_PUBLIC_CF_ANALYTICS_TOKEN` is set; no clicks or form submissions are measured.

## Gotchas found while testing

- **HeroUI `Modal` animations:** react-aria waits for the backdrop/container CSS animations before mounting/unmounting and silently gets stuck (dialog stays open after Escape/Cancel/save). `globals.css` therefore sets `animation: none` on `[data-slot="modal-backdrop"|"modal-container"]` and animates entry on `[data-slot="modal-dialog"]` instead. Keep new overlay animations on inner elements, not those two.
- **Focus after closing a controlled modal:** react-aria doesn't restore focus to the trigger when the button doesn't take focus on press; `scheduling-view.tsx` refocuses it explicitly (`handleOpenChange`).
- **Map in dialogs:** `.site-map` has a fixed height; inside a smaller container override it (see `.formMap` in `scheduling-view.module.css`) or the edit controls get clipped.
- **WebGL in the in-app browser is disabled**, so the 3D drone only shows its fallback there. To see it, drive headless Chromium from `~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome` over CDP with `--use-angle=swiftshader --enable-unsafe-swiftshader`.
- **HeroUI `Tabs.Tab` is `w-full`:** don't put `flex-wrap` on `Tabs.List` or every tab takes its own row; use `width: auto` on the tabs (see `flight-review.module.css`).
- **Reading text:** every `p` gets `max-width: var(--measure-body)` by default (`:where(p)` in `globals.css`, zero specificity; lead lines use `--measure-lead`; in `ch`; Instrument Sans is narrow, 1ch ≈ 1.5 characters, so 46ch ≈ 70 characters) and size with `--text-lead|body|small`; on the landing, text over the relief texture sits on the feathered veil of `.sectionHead::before`. Rules in `docs/UX_GUIDELINES.md` «Texto de lectura».
- **Headings:** one `h1` per route, no skipped levels; size comes from the `--heading-page|object|section|sub|group` tokens by role (scale in `DESIGN.md`, rules in `docs/UX_GUIDELINES.md` «Títulos y encabezados»), always weight 700. `EmptyState` takes `level={2}` when it follows the page title directly.
- **Type floor is 12px** (the primary user is a 56-year-old on a desktop); don't reintroduce 8–11px text.
- **Verification:** `npm run dev`/`dev:webpack` often already runs on :3000 (check `ss -ltnp`); don't run `npm run build` against a live dev server without checking it still responds. In the in-app browser, HeroUI buttons ignore JS `.click()` (use real clicks) and screenshots may not paint portals — confirm with DOM queries.

## Conventions that aren't obvious from the code

- Identifiers in English, user-facing copy in Spanish (`es-CO`, plain producer language). Core names: `company`, `site`, `zone`, `flight`, `finding`, `report`; `farm`/`plot` only for agro-specific context.
- Keep pages/layouts as server components; place `use client` at the narrowest interactive component. Model mutually exclusive UI states as a union type, not boolean combos.
- Every data view needs loading/empty/error/content states; every action needs a visible result and recovery path.
- When several agents work in parallel, they own distinct files; shared changes (tokens, `demo-context`, `types.ts`, `globals.css`) go through the integrator. Verify the changed flow on desktop and mobile, keyboard, and reduced motion, then run `npm run check`.
- WCAG 2.2 AA is the target; never claim certification.
- Screen organisation: one primary object per page (big, first), master → detail in `components/ui/stage-drawer.tsx`, at most four peer tabs via `components/ui/section-tabs.tsx` (critical alerts stay visible outside tabs), long or secondary text in `<details>`. Reasoning and sources: `docs/context/organizacion-de-pantallas.md`.

**Pre-flight checklist.** `features/flights/planning/preparation-items.ts` defines 15 items in 5 groups. `Flight.checklist` stores completed item labels, so the seeded labels in `demo-data.ts` must keep matching those strings.
